# Gemini 기반 AI 서비스 개선 계획

## 1. 목적과 현재 상태

본 계획은 `PRD.md`의 F-01, 성공조건 3·5·6, 예외 처리 E-08~E-13을 유지하면서
현재 사주·띠·별자리 계산 서비스의 Gemini 활용 품질과 운영 안정성을 높이는 후속 로드맵입니다.

현재 구현 상태:

- `POST /api/fortune` 서버 Route Handler에서 Gemini를 최우선 호출합니다.
- API 키는 `GEMINI_API_KEY`, 모델은 `GEMINI_MODEL`로 관리하며 브라우저 번들에 노출하지 않습니다.
- 기본 모델은 10초 응답 목표에 맞춘 `gemini-3.5-flash-lite`입니다.
- AI 호출은 8.5초에 중단하고 전체 사용자 요청은 10초 이내 종료합니다.
- AI 응답 실패 시 오행 기반 규칙 엔진으로 결과를 반환해 서비스 가용성을 유지합니다.
- AI 응답은 Zod 기반 후처리로 성향 3개, 상세 3개, 별점 1~5를 보장합니다.
- 사용자 생년정보와 결과는 DB에 저장하지 않습니다.

## 2. 목표 지표

| 영역 | 목표 |
|---|---|
| 응답 성공률 | Gemini 또는 Fallback을 포함한 API 성공률 99% 이상 |
| 응답 시간 | p95 10초 이하, Gemini 호출 제한 8.5초 |
| 형식 안정성 | UI 렌더링 가능 응답 100%, 성향·상세 각 3개 |
| AI 활용률 | Gemini 정상 응답 비율을 측정하고 Fallback 원인을 구분 |
| 개인정보 | 생년정보·API 키·원문 응답을 영구 로그에 저장하지 않음 |
| 비용 안전성 | 요청별 출력 길이 제한 및 일일 사용량 경보 기준 마련 |

## 3. 단계별 개발 계획

### Phase 1. Gemini 연결 안정화

- [x] 서버 전용 `GEMINI_API_KEY` 설정
- [x] `GEMINI_MODEL`을 통한 모델 교체 가능 구조
- [x] API 키를 URL 대신 `x-goog-api-key` 헤더로 전달
- [x] 8.5초 AbortController 및 규칙 엔진 Fallback 유지
- [x] 실제 Gemini 요청 스모크 테스트와 응답 출처 확인 (`gemini-3.5-flash-lite`, HTTP 200)
- [x] 필수 환경변수 누락을 명확히 경고하는 서버 설정 검증 추가

완료 조건: 유효한 키로 Gemini 응답을 받고, 키 누락·잘못된 키·타임아웃에서 각각 안전한
Fallback이 동작해야 합니다.

### Phase 2. 구조화 출력과 타입 안전성 강화

- [x] Gemini 구조화 출력 스키마를 API 요청에 명시
- [x] `any` 응답을 `unknown`으로 받고 Zod `safeParse`를 통과한 데이터만 사용
- [x] JSON 코드펜스, 빈 후보, 차단 응답, 비정상 점수에 대한 파서 테스트 추가
- [x] 프롬프트와 응답 스키마를 Route Handler에서 별도 모듈로 분리
- [x] 모델명, 프롬프트 버전, 스키마 버전을 상수로 관리

완료 조건: 손상된 AI 응답을 주입한 테스트에서도 API가 예외 없이 정상 결과 또는 명확한
Fallback 결과를 반환해야 합니다.

### Phase 3. 품질 평가 체계 구축

- [x] 띠·별자리·오행 조합을 포괄하는 고정 평가 입력 세트 작성
- [x] 관련성, 반복성, 구체성, 문체, 금칙 표현을 평가하는 자동 체크 도입
- [x] 동일 입력 반복 호출 시 문구 다양성과 핵심 사실 일관성 측정
- [x] 규칙 엔진 결과와 Gemini 결과를 구분하는 응답 헤더 및 구조화 이벤트 설계
- [x] 프롬프트 변경 전후 회귀 평가 절차 문서화

완료 조건: 프롬프트나 모델 교체 시 기준 평가 세트에서 품질 저하 여부를 정량적으로 비교할
수 있어야 합니다.

### Phase 4. 운영·비용·보안 강화

- [x] 생년정보와 AI 원문을 제외한 지연시간·상태·Fallback 사유만 구조화 로깅
- [x] `success`, `timeout`, `provider_error`, `parse_error` 지표 구분
- [x] IP 또는 세션 단위의 가벼운 요청 제한 적용 (인메모리 분당 10회)
- [x] 출력 토큰과 응답 길이 상한 설정
- [x] API 키 교체 절차 및 배포 환경별 Secret 설정 문서화
- [x] 운세 결과가 오락·참고 목적임을 명확히 안내하고 의료·법률·재무 판단 유도 금지

완료 조건: 키가 코드·로그·클라이언트에 노출되지 않고, 장애 원인과 비용 증가를 개인정보 없이
파악할 수 있어야 합니다.

### Phase 5. 제품 경험 확장

- [ ] 결과 문체를 선택할 수 있는 프리셋 검토(후속 제품 옵션)
- [x] AI 응답에서 오늘 실천할 행동 한 가지를 구조화 필드로 제공
- [x] 공유 URL 길이 제한과 E-16 단계별 재시도 보완
- [ ] 사용자 피드백을 저장하지 않는 범위에서 세션 내 만족도 표시 검토(후속 제품 옵션)
- [ ] 주간·월간 운세 및 AI 채팅은 기존 PRD 범위 밖이므로 별도 승인 후 추진

## 4. 권장 실행 순서

1. 실제 Gemini 스모크 테스트와 출처 확인
2. 구조화 출력 및 `unknown` + Zod 검증
3. 고정 평가 세트와 회귀 테스트
4. 개인정보 없는 관측성과 요청 제한
5. 제품 경험 확장

Phase 1~2는 출시 안정성에 직접 영향을 주므로 우선 진행하고, Phase 3 이후는 운영 데이터와
제품 목표를 확인하며 순차 적용합니다.

## 5. 배포 체크리스트

- [ ] 배포 환경에 `GEMINI_API_KEY` Secret 등록
- [ ] 필요 시 `GEMINI_MODEL` 등록, 미등록 시 기본 모델 사용 확인
- [ ] 클라이언트 번들에 키 문자열이 포함되지 않음을 확인
- [ ] 정상·키 오류·타임아웃·비정상 JSON 경로 검증
- [ ] p95 응답 시간과 Fallback 비율 확인
- [ ] 개인정보 및 AI 원문이 로그에 남지 않음을 확인
